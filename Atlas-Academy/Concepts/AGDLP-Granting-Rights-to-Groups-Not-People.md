This module is the missing half: *why authorization flows through a fixed chain of nested groups instead of being granted to people*, and why a model can be "structured" long before it's "enforced."

## The Concept

Authentication proves who you are; **authorization decides what you may do** — and the discipline that keeps it maintainable is that a permission is **never granted to a person.** It flows through a fixed chain: **A**ccounts → **G**lobal role groups → **D**omain-**L**ocal resource groups → **P**ermission. AGDLP.

Why the indirection, which looks like bureaucracy until you run it at scale: **roles and resources change independently.** Put a *person* in a **global** group that names their role (`G-Finance`), put the *permission* on a **domain-local** group that names a resource (`DL-FinanceShare-Modify`), and make the global a member of the domain-local. Now onboarding is *"add the user to one global,"* a new share is *"make one domain-local and grant it,"* and access reviews read cleanly (who's in the role, what the role can reach) — **and nothing is ever written directly onto an ACL**, where it would be invisible and un-auditable. Grant a permission straight to a user and you've created a fact that lives only in a file-system ACL nobody enumerates; AGDLP keeps every grant in the directory where it can be listed.

On top of the grouping sits the **tier boundary**. Admin rights flow *only* through the per-tier admin globals, and a higher-tier credential is **denied logon** to a lower tier by policy — the control that makes "a Tier-0 account structurally cannot sign in to a workstation" true rather than merely intended. Which surfaces the sharpest idea in the whole module: **a model is *structured* the moment the groups and OUs exist, but *enforced* only once the deny-logon policies are actually linked.** The gap between those two states is real, dangerous, and must be stated — a boundary that is only OU placement is a diagram, not a control. And the last rule: the tier you protect most is reachable only from a known, hardened surface — Tier-0 admin comes **only from the PAW**, and everything else reaching identity is auth-only.

## The Atlas Example (real artifacts)

- **AGDLP, live.** The tier admin globals **`G-Tier0-Admins` / `G-Tier1-Admins` / `G-Tier2-Admins`** (+ **`G-IT-Staff`**) are the only source of admin rights, each scoped to its tier — ✅ **device-verified 2026-07-22**; department role globals (`G-Sales`, `G-Finance`, …) grant *resource*, not admin, access and arrive with the user population (📋). Read-back: `Get-ADGroupMember G-Tier0-Admins`. (`STD-0002` R1/R2.)
- **The deny-logon control ([`STD-0002` R3](../../00-Atlas-Foundation/Standards/STD-0002-Access-Control.md)).** Five cross-tier **deny-logon-rights GPOs** enforce the boundary — a Tier-0 identity is *denied interactive/RDP/network logon* on Tier-1/2 hosts and vice-versa — **never linked at the domain root**. This is the control behind the flagship **"Tier-2 can't touch Tier-0"** proof; the itemized five + the denial test live in [`Validation-and-Adversarial-Testing`](../../Labs/Lab-02-Cisco-Core/Operations/Validation-and-Adversarial-Testing.md). **Status: ⬜ not built — unblocked** now the groups exist (the single most important open access control).
- **Tier-0 only from the PAW ([`STD-0002` R4](../../Labs/Lab-02-Cisco-Core/Devices/PAW01-Tier0-Admin/)).** Interactive Tier-0 admin comes only from [`PAW01`](../../Labs/Lab-02-Cisco-Core/Devices/PAW01-Tier0-Admin/) (east-west **flow #23**); everything else reaching the identity micro-zone is auth-only — LDAPS/Kerberos/DNS (**flow #9**, *"the only thing that reaches Tier 0"*), rendered in the [flows matrix](../../Labs/Lab-02-Cisco-Core/Architecture/Atlas-East-West-Allowed-Flows-Matrix.md). `t0-seth` is in **Protected Users** (the credential half — [The Credential Layer](./The-Credential-Layer-PSOs-LAPS-and-gMSA.md)).

## What Went Wrong (real troubleshooting history — the best teacher)

- **Structured, but not enforced — said out loud.** The estate's own status is that the tier **groups are ✅ built** while the **deny-logon GPOs are ⬜** and the **PAW is 📋** — so the tier boundary today is *OU/GPO placement only, not enforcement*, and `STD-0002` marks it exactly that way. The flagship *"Tier-2 can't touch Tier-0"* proof **cannot pass yet**, and the honest thing is that a closed *design* gap with an unbuilt mitigation is still an **open** one (`POL-0001` — a control is real only when a read-back refuses the wrong actor; the [Risk as a Living Register](./Risk-as-a-Living-Register.md) lesson). Claiming the boundary as done because the groups exist would be the exact failure `POL-0006` forbids.
- **The domain-root trap.** A deny-logon GPO linked at the **domain root** denies *everyone everywhere* — including you — so the five must be linked at the **tier OUs**, never the root. A control placed one level too high stops being protection and becomes an outage (a violation signature `STD-0002` names explicitly).
- **A permission granted straight to a user.** The moment a right is written directly onto a resource ACL instead of through a domain-local group, it leaves the directory and lives only in a file system nobody audits — the drift AGDLP exists to prevent, and the reason `STD-0002` R1 forbids direct grants.

## How to Explain This in an Interview

*"Authorization in my environment never grants a permission to a person — it follows AGDLP: accounts go into global groups that name a role, permissions go onto domain-local groups that name a resource, and the global is a member of the domain-local. The reason is that roles and resources change independently, so onboarding becomes 'add the user to one global,' a new share becomes 'make one domain-local,' and nothing ever gets written directly onto an ACL where it's invisible to an access review. On top of that I run tiering: admin rights only flow through per-tier admin groups, and a higher-tier account is denied logon to lower-tier machines by GPO — linked at the tier OUs, never the domain root, because a deny-logon at the root locks out everyone including me. And the honest part I'd volunteer: my groups are built and verified, but the deny-logon GPOs aren't linked yet, so right now the tier boundary is structured, not enforced — my flagship 'a Tier-2 account can't RDP a domain controller' test can't pass until I build them, and I don't get to call it done until it can."*
