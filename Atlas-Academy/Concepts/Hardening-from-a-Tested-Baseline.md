## The Concept

Hardening is not a list of clever settings you think up. It is starting from a **tested baseline** — a published, peer-reviewed set of secure defaults (the **CIS Benchmarks**, Microsoft's **Security Compliance Toolkit / Security Baselines**) — and then layering your estate's specifics on top. The reason to *import* a baseline rather than hand-pick settings is coverage and honesty: a baseline is hundreds of individually-justified settings vetted by many people, delivered as something you apply and measure against; hand-selecting is how you silently miss the setting you didn't know to look for, and how "possibly applied" creeps in. A baseline is a **tested starting point, not the finish line** — you import it, then link your own policies (a stricter password rule, your logon banners) *on top*, so your deltas are visible against a known-good floor instead of lost in a hand-built pile.

Two disciplines the baseline itself won't give you:

**Close the attack surface you're not using — and *record* the ones you keep.** Every interface, service, and port with no assigned purpose is disabled, because an enabled-but-unused door is pure downside: it can't help you and it can be walked through. But "disable everything unused" has a twin rule that's easy to skip — **any port you keep enabled carries a written reason** (an uplink, a planned role, a break-glass recovery path). *"Available" is not a state.* An enabled port with no recorded purpose is indistinguishable from an oversight, so the next person leaves it — or an intruder finds it.

**A hardening tick is a claim until a read-back proves it.** The single most common hardening lie is marking a control "done" from the *config line that should enable it* rather than the *runtime output that shows it working.* A control is in one of exactly two honest states: **enabled and verified** (a `show`/`get` read-back confirms it), or **formally accepted out of scope by a decision** (an ADR) — never a stale profile attached to a box, looking protective, doing nothing. And because hardening *removes* things, it can remove your own way back in — so it's done **recovery-first**, over a path the change can't sever (see [Out-of-Band Recovery](./Out-of-Band-Recovery.md)).

## The Atlas Example (real artifacts)

**The imported baseline, then the layers on top.** The Windows domain starts from the **Microsoft Security Baseline imported as GPOs** (device-verified at the DC build's Stage 7a) — a tested floor — and Atlas then links its **Wave-A** policies and the **`PSO-FinanceHR`** fine-grained password policy on top ([DC `Build-Checklist`](../../Labs/Lab-02-Cisco-Core/Devices/DC-Domain-Controllers/Build-Checklist.md)); the deltas are visible against the baseline instead of hand-built. The network devices each carry a **`CIS-Hardening-*`** baseline ([`1941`](../../Labs/Lab-02-Cisco-Core/Architecture/CIS-Hardening-1941.md) · [`SW01`](../../Labs/Lab-02-Cisco-Core/Architecture/CIS-Hardening-SW01.md)) — SSH v2 / CTR-ciphers-only / DH-2048 / Type-9 secrets, device-verified 2026-07-22 (the crypto half is [`STD-0004`](../../00-Atlas-Foundation/Standards/STD-0004-Encryption.md)).

**The decision-not-"possibly-applied" rule.** FGT01's UTM is either *enabled and verified working* or *formally accepted out of scope by an ADR* — the estate reversed an earlier "no UTM" decision rather than leave a profile that looks protective and isn't (`POL-0007`'s "decisions, not possibly-applied"). Unused interfaces get disabled with the reason for any exception recorded ([`CM-0004`](../../Labs/Lab-01-Mikrotik-Core/Devices/FGT01-NS-Firewall/Changes/CM-0004-Disable-Unused-FGT01-Interfaces.md)).

## What Went Wrong (real troubleshooting history — the best teacher)

- **Five live, undocumented ports on the *perimeter firewall* ([`CM-0033`](../../Labs/Lab-01-Mikrotik-Core/Devices/FGT01-NS-Firewall/Changes/CM-0033-FGT01-Five-Live-Undocumented-Ports.md)).** FGT01's `internal3`–`internal7` plus a factory `dmz` L3 interface were up and unassessed on the estate's edge device — the surface a "hardened" firewall was supposed to have closed. The lesson is `POL-0007`'s core: you can't harden what you never enumerated, and *"available is not a state."*
- **The enabled port nobody had decided to keep ([`CM-0015`](../../Labs/Lab-01-Mikrotik-Core/Devices/MKT01-Core-Router/Changes/CM-0015-Disable-MKT01-ether2.md)).** MKT01's `ether2` was enabled and undocumented — not malicious, just never *decided*. Disabling it (and recording the ones kept, like the `ether4` recovery port) is the discipline that turns a pile of ports into a set of decisions.
- **Ticks made from config lines, not read-backs.** `POL-0007` records that *five false hardening ticks* came from reading a config line as proof instead of the runtime output — the same discipline as [`A-Completed-Command-Is-Not-Evidence`](./A-Completed-Command-Is-Not-Evidence.md). A hardened box is one whose controls you *read back*, not one whose config you *hoped applied*.
- **Hardening that locked out its own operator.** The 1941's SSH hardening self-blocked the network path mid-change; it was finished **over the serial console** because the recovery path was proven first (the [Out-of-Band Recovery](./Out-of-Band-Recovery.md) lesson — *hardening deletes the way back in*).

## How to Explain This in an Interview

*"I don't hand-invent hardening settings — I import a tested baseline and then layer my own on top. On Windows that's the Microsoft Security Baseline as GPOs, then I link my Wave-A policies and a stricter password policy for finance over it; on the network gear it's the CIS benchmark per device. The reason is coverage and honesty: a baseline is hundreds of vetted settings I apply and measure against, whereas hand-picking is how you miss the one you didn't know about. Two rules the baseline doesn't give you: close every port and service you're not using, and — the part people skip — write down the reason for any you keep open, because 'available' isn't a state and an undocumented open port is indistinguishable from a mistake. I learned that one the hard way: my perimeter firewall had five live undocumented interfaces nobody had assessed. And I only mark a control done when I read it back from the device, not from the config line that's supposed to enable it — a stale profile that looks protective is worse than an obvious gap. Last thing: hardening removes things, so it can lock you out, which is why I always prove the recovery path first — I finished a switch's SSH hardening over the serial console after the change blocked the network path."*
