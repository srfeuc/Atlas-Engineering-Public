# Out-of-Band Recovery (one module)

> **Atlas Academy — Concepts.** A "why it works" module (`Academy/README` 4-part format). Every claim points at a **real Atlas artifact** — a real console spec, a real recovery-path build, a real "we almost deleted the way back in" incident. The *controls* live in [`STD-0003` Physical & Console/OOB](../../00-Atlas-Foundation/Standards/STD-0003-Physical-Security.md) and the *step-by-step* in the [Recover-a-Locked-Out-Router playbook](../Playbooks/Recover-a-Locked-Out-Router-Out-of-Band.md); this page explains the **reasoning** so the discipline is understood, not just followed. One home per fact (`POL-0004`) — the device pages and the standard own the values; this page links them.

> **The gap this closes ([`STD-0003` Learn-it](../../00-Atlas-Foundation/Standards/STD-0003-Physical-Security.md)):** the standard requires a reachable console break-glass, a dedicated out-of-band path, and honestly-marked gaps — but a standard says *what*, not *why*. `STD-0003` flagged that an *out-of-band recovery / "hardening deletes the way back in"* Concept was **warranted** (the `CM-0021`/`CM-0012` lessons). This is it: why a recovery path is a control you build on a healthy device, why the same hardening pass that closes attack surface can close your own door, and why an unneeded-looking fallback and a genuinely unneeded one are indistinguishable until the outage.

## The Concept

**Out-of-band recovery is the way back into a device when the normal way in is gone** — you pushed a bad firewall rule, disabled the wrong port, lost or changed the management address, or the box won't boot its config. "Out-of-band" means the recovery path does **not depend on the thing that broke**: a serial console works when IP routing is dead; a Layer-2 path works when addressing is wrong; a separate management network works when the production one is down. The normal path is *in-band* — it rides the same plumbing you're trying to fix, so it's exactly what a bad change takes away.

Two truths turn "keep a console handy" into a discipline.

**One — a recovery path is invisible until you need it, so it gets deleted in good faith.** A fallback that has never been used looks *identical* to a fallback that isn't needed. Both are quiet. Both show no activity. So a well-meaning engineer doing housekeeping sees an idle interface or an "unused" network and retires it — and discovers only during the next outage that it was the one thing that would have worked. *"A control that has never been needed looks identical to a control that is not needed"* (`ADR-0013`). The corollary: **document what a recovery path is for, on the device**, or someone acting in good faith removes it.

**Two — hardening deletes the way back in.** The same pass that closes attack surface — disabling services, shutting ports, locking down the management plane — can close *your* door with it. Harden SSH wrong and you can lock yourself out over the network; disable "unused" ports and you may shut the one you'd have recovered on. So the rule is **recovery-first**: prove the way back in *before* you make the change that could need it, and keep a working session open as a live rollback while you do.

Put together, they give the real principle: **build and prove the recovery path on a *healthy* device.** A cable, a console, or a break-glass path tested for the first time during an outage is a *hope*, not a control (`ADR-0011`). The ladder to design is least-destructive-first — normal in-band path → an independent out-of-band path the break can't kill → factory reset and rebuild as the last resort — and the honest part is marking the rungs you *haven't* actually built, rather than ticking a path you can't hold.

## The Atlas Example (real artifacts)

**The serial-console break-glass, proven under fire (`STD-0003` R1).** The Cisco 1941 and SW01 keep a serial console — **9600 8N1, `line con 0 login local`** (local `ciscoadmin`) — reachable before any SSH/management change can lock you out. This isn't theoretical: the 1941's CIS-hardening pass was completed **over the console when the SSH change self-blocked** (2026-07-22, ✅ device-verified) — the recovery-first rule earned its keep the day it was written. MKT01 (an RB1100AHx4) has its own serial spec — **115200 8N1, flow control NONE, a null-modem (crossover) cable, a genuine FTDI chip, router-port female → cable-end male** — captured in the [console-recovery spec](../../Labs/Lab-01-Mikrotik-Core/Devices/MKT01-Core-Router/Console-Recovery-Cable-and-Settings.md). [`ADR-0023`](../../00-Atlas-Foundation/Decisions/ADR-0023-1941-Core-MKT01-East-West-Firewall-Topology.md) makes a *tested* console a **hard prerequisite** before MKT01 becomes the default-deny east-west firewall — because *a default-deny box with no console is one bad rule from total lockout.*

**The Layer-2 break-glass — an independent path (`CM-0018`).** MKT01 spent most of its life with **no console**, so the only out-of-band path was **MAC-WinBox**: WinBox over Ethernet, not IP. Because it speaks Layer 2, the **IP firewall never evaluates it** — it works even when routing and addressing are broken, which is exactly the failure it exists for. It's scoped to a `RECOVERY` interface list ([`CM-0018`](../../Labs/Lab-01-Mikrotik-Core/Devices/MKT01-Core-Router/Changes/CM-0018-Establish-MKT01-MAC-WinBox-Recovery-Path.md)) — and the *scoping* is itself a lesson in the tension every recovery path carries. Every enabled port that answers MAC-WinBox is a login prompt, so ten live sockets on the core router in an unlocked room is **ten open doors**; scoping to one port (`ether4`) *"reduces ten doors to one."* A source-MAC allow-list was **rejected** — a MAC is spoofable in one command, *"a speed bump that looks like a lock,"* which is worse than an obvious gap because you stop watching the door (the real room control is SW01 `port-security`, deferred and named, not faked). And you **can't disable every port** — you can't log in to re-enable one — so one always-open port is *"the irreducible price of having a recovery path at all."* The path was proven by a **live MAC-connect from `ether4`**, with an honestly-recorded ~15-second session drop (`ADR-0016`).

**The out-of-band path that isn't (yet) — marked, not faked (`STD-0003` R2).** PVE01's **iDRAC** is the *intended* out-of-band path, but today it isn't out-of-band: it rides the shared LOM (so it **dies with SW01**, step one of any teardown) and is **blocked by `CM-0012`** — a dead CR2032 means the BMC can't hold its settings. Rather than tick it, [`ADR-0017`](../../00-Atlas-Foundation/Decisions/ADR-0017-Defer-CM-0012-CMOS-Battery.md) **defers it in the open** — *"a tick you did not earn is a lie"* — and [`050`](../../Labs/Lab-01-Mikrotik-Core/Operations/050-PVE01-iDRAC-Onboarding-Runbook.md) unblocks it once the battery is replaced and the board proves it holds config. A recovery ladder is only as honest as the rungs it admits it hasn't built.

**The extreme case — the CA's own recovery artifact (`STD-0003` R3).** The same discipline governs the estate's most irreplaceable secret: the Root CA key lives on **air-gapped, powered-off media**, its passphrases on **paper, two copies, one off-site, never in the same container as the media** ([`049`](../../Labs/Lab-01-Mikrotik-Core/Operations/049-Root-CA-and-Credential-Backup-Runbook.md)). That's out-of-band recovery applied to *custody* — and it links straight to [`STD-0004` R5](../../00-Atlas-Foundation/Standards/STD-0004-Encryption.md) and the [Encryption & PKI concept](./Encryption-and-PKI-in-Atlas.md). (The estate is honest that the encrypted media has **no off-site copy yet** — a named Tier-1 gap, not a hidden one.)

## What Went Wrong (real troubleshooting history — the best teacher)

The estate's recovery discipline was paid for in real incidents, all frozen in Lab-01 (`ADR-0022`; reconcile to the current design — the bridgeLocal/`10.0.0.0/24` recovery net they describe is frozen Lab-01, superseded by the Lab-02 console + iDRAC model, `ADR-0013`).

- **The recovery path four documents described had never existed ([`CM-0017`](../../Labs/Lab-01-Mikrotik-Core/Devices/MKT01-Core-Router/Changes/CM-0017-MKT01-MAC-Server-State-Investigation.md) → [`CM-0018`](../../Labs/Lab-01-Mikrotik-Core/Devices/MKT01-Core-Router/Changes/CM-0018-Establish-MKT01-MAC-WinBox-Recovery-Path.md)).** MKT01's MAC-WinBox path was assumed to exist and was even referenced in build guides — but `mac-winbox` had been `none` the whole time. A MAC-connect returned `MacConnection syn timeout`, and the honest reading was not "we're locked out" but "the path was never built." It was then built for the first time and **proven by doing** — a live MAC-connect — not by reading a setting back. The lesson that came out of it is the sharpest one-liner in the estate: *"Seeing a device in a discovery list is not access. Being able to click Connect is not access. Not being asked for a password is not access. Access is a session. Everything else is the door being visible."*
- **"Retire it, it's inactive" — the good-faith deletion ([`ADR-0013`](../../00-Atlas-Foundation/Decisions/ADR-0013-Retire-bridgeLocal-Recovery-Network.md)).** A future-work doc proposed retiring the "legacy `10.0.0.0/24` network" as routine housekeeping. The device confirmed that network *was* `bridgeLocal` — the admin recovery net two other documents **explicitly forbade removing** — and that its ports read `INACTIVE` simply because no cable was plugged in: *the correct resting state for a fallback, not evidence it's dead.* Worse, MKT01 labelled the address `;;; Legacy flat management` in its own config — *"calling your recovery path 'Legacy' on the device is how it gets deleted by someone acting in good faith."* Reversing a written keep-decision needed an ADR, not a quiet change record — because the reversal would otherwise live somewhere the people relying on the path would never read.
- **Hardening nearly deleted the way back in (`STD-0003` "why").** MKT01 once had **no safe recovery mid-hardening** (`CM-0021`); an *unexplained* hardening line — a disabled port, a tightened service — is exactly how a recovery path disappears, because the next engineer can't tell a deliberate keep from an oversight. It's why the `ether5`–`ether13` disable in `CM-0018` was recorded *with its rationale* and the build guide rewritten so a rebuilt router comes back **with** a recovery path instead of none.
- **The out-of-band path that read "fine" while being blind (`CM-0012` / [`ADR-0017`](../../00-Atlas-Foundation/Decisions/ADR-0017-Defer-CM-0012-CMOS-Battery.md)).** PVE01's iDRAC could have been ticked as "OOB present," but a cipher-0 IPMI probe returning a quiet result was an *expected* quiet, not proof of a working channel — the same error class as reading `INACTIVE` as "dead." The battery fault (`CM-0012`) means the BMC can't hold config, so the honest mark is 📋 deferred, blocked, with the unblock runbook named.

The thread through all four: **a quiet, expected result is not evidence of a working recovery path** — you prove the way back in by walking it, on a healthy device, before you need it. (The same read-it-back discipline as [`A-Completed-Command-Is-Not-Evidence`](./A-Completed-Command-Is-Not-Evidence.md).)

## How to Explain This in an Interview

*"Out-of-band recovery is having a way back into a device that doesn't depend on the thing that broke — a serial console when the network's down, a Layer-2 path when IP is misconfigured, a separate management network. The mistake people make is treating it as an afterthought, and there are two reasons it bites. First, a recovery path you've never used looks exactly like one you don't need — it's idle, it's quiet — so someone doing housekeeping deletes it in good faith, and you find out during the outage. Second, hardening deletes the way back in: the same pass where you disable services and shut ports can lock you out, so I always prove the recovery path and keep a live session open before I make the change. In my lab I hardened a router's SSH over the serial console specifically because the change could self-block, and on a MikroTik with no console I built a Layer-2 MAC-WinBox path and proved it with a real connect — not by reading the setting back, because being visible in a discovery list isn't the same as having a session. And where my out-of-band path wasn't actually independent yet — an iDRAC riding a shared uplink with a dead CMOS battery — I marked it as a deferred gap instead of ticking a box I couldn't stand behind. The rule I take from all of it: a recovery path is a control you build and test on a healthy device, because a cable you first try during an outage is a hope, not a plan."*
