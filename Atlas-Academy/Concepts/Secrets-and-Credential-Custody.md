This is the *why* behind the rule: why exposure can't be undone, why rotation (not deletion) is step one, and why the control that catches a secret has to be tested against the thing that actually happened.

## The Concept

A secret is anything reusable to gain access — a password, passphrase, private key, API token, RADIUS or SNMP shared secret, the contents of a vault. Two ideas make handling them a discipline rather than a habit.

**One — a secret in the wrong place is *burned*, not hidden.** The instinct on discovering a committed secret is to delete it. But you cannot un-expose something that was already exposed: a copy may have been read, forked, cached, or pushed to a server whose retention you don't control. **A repository is not a filesystem** — `git rm` deletes a *name*, not the blob, and `git push --force` doesn't delete a blob from someone else's server. So deletion is never the first move. **Rotation is** — because a rotated secret makes every leaked copy worthless, everywhere, permanently, and it is the *only* remedy that doesn't depend on anyone else's cooperation. Deletion/purge is cleanup you do *after* the secret is already dead. The corollary the estate paid for: **`git push` is a change to a production system** — it moves data to a machine you don't own — and a *private* repo isn't where a secret is safe, it's where a secret is *pending*, one good-faith click from public.

**Two — a rule doesn't enforce itself, and the control must be tested against the real thing.** *"Never commit a secret"* can be written, published, and in force, and still be violated by the very commit that ships it — because **a standard with no mechanical enforcement is a preference.** The enforcement matters more than the wording, and it has to be aimed at how failures actually look. Two traps: **denylisting extensions protects the extensions you thought of** (a passphrase in a `.txt` matches none of them), and a **content scanner only catches shapes it recognises** — an `AKIA…` prefix, a `BEGIN RSA PRIVATE KEY` header — while a bare high-entropy passphrase **has no shape at all**, so the *filename* is the only signal. A control you haven't tested against the real incident is a control you're guessing about.

Around those two ideas sits ordinary custody hygiene, each rule earned: secrets live in the **vault**, not in docs; the one secret that can't be vaulted (the archive passphrase that opens *everything*) lives on **paper**, and **never in the same container as the media it unlocks** — media plus passphrase in one envelope is one envelope that owns your estate. Any procedure that *copies* secret material names, in the same procedure, **who destroys the copy and when** — a create step with no destroy step leaves the thing it created lying around. And a passphrase is composed to **survive a recovery**: entropy from *length*, in characters that don't break the shells you'll type it into at 2 a.m.

## The Atlas Example (real artifacts)

**Where secrets live (`POL-0002` / `STD-0004` R2/R5).** Reusable secrets live in **Vaultwarden**; a doc may *name where* a secret is stored but never contains one that still works (Charter). Device secrets on the boxes are stored as **Type 9 scrypt**, never Type 7/5 — a stored password you can *decrypt* is a stored password an attacker can decrypt (`STD-0004` R2). The Root CA's passphrases are on **paper, two copies, one off-site, never with the media** (`STD-0004` R5 / [`049`](../../Labs/Lab-01-Mikrotik-Core/Operations/049-Root-CA-and-Credential-Backup-Runbook.md)).

**The mechanical control (the part that actually holds).** A **`gitleaks` scan in CI** ([`.github/workflows/atlas-checks.yml`](../../.github/workflows/atlas-checks.yml)) fails a push that carries a secret — content-based, not a local-only hook — plus a **name-based rule** ([`.gitleaks.toml`](../../.gitleaks.toml)) that fires on any file whose *name* says "secret" (`passphrase|secret|credential|password|.env|.key|.pem`), because the default content ruleset provably missed the real one. The estate never runs `git add .` (that's how the scar shipped) and verifies a secret's removal by **counting the old string to zero** (Charter Rule 16), not by trusting that a redaction was appended.

**The custody procedure, with its destroy step (`POL-0002` verification).** A backup that could capture `/etc/ssl` or vault data runs a **pre-archive `ls`** and a **post-archive `tar -tzf`** to prove no secret rode along, and every exposure produces — dated, in a change record — the **rotation *and* the copy-destruction *and* the blast-radius note**, not just one of the three.

## What Went Wrong (real troubleshooting history — the best teacher)

The whole discipline is a distillation of two frozen Lab-01 incidents (`ADR-0022`).

- **The commit that shipped the rule broke it ([`CM-0014`](../../Labs/Lab-01-Mikrotik-Core/Change-Management/CM-0014-Archive-Passphrase-Committed-to-Repository.md)).** `Archive passphrase.txt` — the GPG passphrase for the archive holding *both CA keys, plaintext RADIUS secrets, and the whole Vaultwarden DB* — was committed to the repo root **in the same commit (`ac2182f`) that shipped `049`, the runbook forbidding it**, both halves staged by `git add .`. Every earlier finding in the estate was caught by reading a *device* back; this one was caught by reading the *repository* — the corollary being *the repository is also a device, and nobody was reading it back.* The cascade of lessons:
  - **The `.gitignore` didn't catch it** — it denylisted *extensions* (`*.key`, `*.conf`…); a file named `Archive passphrase.txt` matched none. *"Denylisting file extensions protects the extensions you thought of."*
  - **The content scanner didn't catch it either** — tested against the *real leaked value*, `gitleaks` default said *"scanned ~25 bytes… no leaks found"* and committed it cleanly, even though it blocked a textbook AWS key. *"A bare high-entropy passphrase has no shape… the filename was the only signal."* The fix inverted the estate's own note that content-scanning is "the control" — a **name-based rule** was added and proven on the exact file. The meta-lesson: **test your control against the thing that actually happened**, not a textbook example.
  - **Rotation came first, deletion second** — the value was rotated (new passphrase generated *in the vault*, the archive re-encrypted and **proven by decrypting from paper** — because `gpg` exiting 0 on encrypt is a *claim*, opening the result is *evidence*), and only then was history purged with `git filter-repo` and **verified unreachable from a fresh mirror clone of GitHub** (a server-side check local objects can't fake). A force-push alone does **not** remove the blob from GitHub.
  - **The visibility trap** — Atlas is a portfolio project, so *"make the repo public"* is the single most likely future action, and it would disclose the commit in the same instant. That constraint had no home, so it became a decision: [`ADR-0010`](../../00-Atlas-Foundation/Decisions/ADR-0010-Atlas-Repository-Publication-Preconditions.md) — the repo must not go public until the purge is complete. *"A private repository is not where secrets are safe. It is where they are pending."*
  - **The rotated-out passphrase was itself a defect** — it contained `!`, `^`, `&`, `@` and failed three ways in three tools during the very recovery it existed for (bash history expansion, the PowerShell parser, paste-mangling). Standard adopted: **long, ASCII, letters/digits/`-`/`_` only — entropy from length, not from characters that break the tools you need.**
- **The rotation that created its own exposure ([`CM-0010`](../../Labs/Lab-01-Mikrotik-Core/Change-Management/CM-0010-CA-Passphrase-Rotation-and-Exposed-Key-Destruction.md) / [`ADR-0009`](../../00-Atlas-Foundation/Decisions/ADR-0009-Intermediate-CA-Not-Treated-as-Compromised.md)).** An earlier backup procedure created `.bak` copies of the CA keys **wrapped in the old passphrase** and had *no destroy step*, so key material and the passphrase that opens it sat on one workstation for ~15 hours. The remedy became a rule — **rotate a leaked passphrase before any backup, never the reverse** — and, more importantly, a **Phase 0 inventory**: *find every copy before you touch any*. That step found a **second, byte-identical archive on an external `E:` drive**; rotating only the first copy would have produced a beautifully documented change record and *zero* security improvement. **A create step with no destroy step, and a narrative with no line that asks "and did you destroy them?", is how a secret survives its own rotation.**

## How to Explain This in an Interview

*"My rule is: a secret in the wrong place is burned, not hidden — so the first move is always rotate, never delete. You can't un-expose something; a git history rewrite doesn't even remove the blob from GitHub's servers, and a force-push doesn't delete it from a fork. Rotating the secret is the only step that makes every leaked copy worthless without needing anyone else's cooperation; the purge is just cleanup you do afterward. The incident that taught me this was a backup passphrase committed to a repo root — in the same commit that shipped the runbook forbidding it — and the sharp part is *why the guards missed it*: the .gitignore denylisted file extensions and a `.txt` matched none, and the content scanner only recognises shapes like an AWS key prefix, so a bare high-entropy passphrase with no shape sailed straight through. We only knew because we tested the scanner against the actual leaked file instead of a textbook example, and it committed it cleanly — so we added a rule that fires on the filename. Since then: secrets live in a vault, the one passphrase that can't be vaulted lives on paper and never in the same place as the media it unlocks, every backup procedure names who destroys the copy it makes, and passphrases are long ASCII so they don't break the shell during the recovery they exist for. And because it's a portfolio repo, we wrote down that 'make public' is a destructive action until the history is clean — a private repo isn't where a secret is safe, it's where it's pending."*
