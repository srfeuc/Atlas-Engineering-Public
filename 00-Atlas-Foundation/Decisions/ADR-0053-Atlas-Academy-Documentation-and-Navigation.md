## Context

The Academy is being grown from a study aid into the estate's **operational knowledge base** (`Academy-Vision-and-Scope.md`): the offline, shareable, *searchable-by-problem-name* briefcase you reach for when something breaks. It already has three coherent layers — **Cert-maps** (*what to test*), **Concepts** (*why it works*), and the **Command-Library** (*how to check it*) — but it lacks the **action layer** (*what do I actually do when something is broken or needs operating*), and it has no written standard for *how an Academy doc is made and found*. The per-device Standard (`ADR-0037`) doesn't fit: the Academy is organized **by concept / command / problem / cert**, cross-device, not by a device's folder shape. The operator asked for this to have its own home ("maybe the Academy needs its own ADR for how documentation is made in this folder, as it will be different"), grounded in the certification pages ("so we know what we actually have to test, and what the methods to configure and troubleshoot are"), under a **strict 3-click rule** — and scoped it plainly: **do Playbooks now; Runbooks come when we get to automation.**

## Decision

Adopt an **Academy Documentation Standard** (Global) with the layers, the Playbooks action doc-type, the cert-grounded spine, and the navigation rule below.

### 1. The Academy's layers — each answers one question
| Layer | Question it answers | Home | Status |
|---|---|---|---|
| **Cert-maps** | *What do we have to test?* (exam objective → Atlas lab → status) | `Atlas-Academy/*-Lab-Map.md` | live |
| **Concepts** | *Why does it work, and how does it fit?* (4-part module) | `Concepts/` | live |
| **Command-Library** | *How do I check / verify it?* (platform-first; healthy vs broken) | `Command-Library/` | live |
| **Playbooks** 🆕 | *What do I do when it's broken / how do I operate it?* (scenario → diagnosis → fix) | `Playbooks/` | **this ADR** |
| **Runbooks** | *How do I do / automate a technique?* (JSON · Python · PowerShell · IaC · Linux CLI) | `Runbooks/` (planned) | **deferred → arrives with the automation work** (`ADR-0048` / Backlog #19/#7) |
| **House-style** | *How do we write it to teach?* | `Atlas-Teaching-Patterns-and-House-Style.md` | live |

### 2. The Playbooks action layer — the operator's briefcase
`Atlas-Academy/Playbooks/` is the **operational / troubleshooting** action layer: *the thing broke, or I need to operate it — what do I do?* Each Playbook is a **scenario keyed by the problem name** — the vision doc's named scenarios (port conflicts, connection testing, blocked/dropped traffic, reading logs, per-appliance inspect-and-troubleshoot, "a device is down"). Rules:
- **Filename = the problem name** (`Port-Already-In-Use.md`, `Trace-a-Blocked-Flow.md`) — the briefcase principle: searchable, and a 1:1 map to a ticket title.
- **Scenario-first, not platform-first** — you search by *the problem you have*; a blocked-flow trace spans four platforms. (The Command-Library stays platform-first for *verification commands*; Playbooks link down into it, `POL-0008`.)
- **Kept current by use** — a Playbook is written/updated when a real method is used, not speculatively (`ADR-0049`; `POL-0006`).

**Runbooks are a distinct, deferred doc-type.** The *"how do I do / try a technique"* content (JSON, Python, PowerShell, automation/IaC, Linux CLI) becomes a sibling **`Runbooks/`** layer **when the automation work lands** (`ADR-0048`; Backlog #19/#7) — not now. Playbooks (fix/operate) and Runbooks (build/automate) will cross-link, but this ADR builds only Playbooks.

### 3. The cert-grounded spine (how the layers tie together)
The **cert-maps are the index that grounds the action layer.** Every exam objective decomposes into Academy entries, and the `Playbooks/README.md` index carries a **cert-objective column** so you navigate from *"what I must test"* straight to the doc:

> **objective** → **Command-Library entry** (verify it) · **Playbook** (troubleshoot / operate it) · **Concept** (why it works) · *(later)* **Runbook** (configure / automate it)

This is what "grounded in the certification page first" means: the cert map tells us *what methods to troubleshoot and operate* we owe, and each becomes a Playbook (with the configure-it Runbook following in the automation phase).

### 4. The strict 3-click rule
**Every Academy doc is reachable in ≤ 3 clicks from the repo front door**, via exactly one middle index:
`root README (or the Academy front door) → a layer index (Concepts/README · Command-Library/README · Playbooks/README · a cert-map) → the doc.`
No Academy doc may be more than one index deep. If a layer grows so a doc needs a second sub-index, that is a **Review Trigger**, not a quiet fourth click. (This makes the estate's standing "three-click rule" explicit for the Academy.)

### 5. The per-Playbook template (the shape every Playbook copies)

In order: **Frontmatter** · **provenance banner** · **the one-line problem** (restates the searchable name) · **Symptoms & search terms** 🆕 · **On this page** 🆕 · **Cert anchor** · **Grounded in** · **① Pin it down** · **the diagnosis path** (each step carries **per-step provenance** 🆕) · **the fix** (+ prove it) · **If still broken** · **Gap / what this closes** *(optional)* 🆕 · **Worked example → the CM/MC doc** *(where a clean case exists)* 🆕 · **Related** · **Worked log** · **Change Log**. Markers ✅/🟡/📋; **never invent output** (`POL-0001`) — an unverified method/capture is 🟡 until a real read-back is pasted. The **golden-template reference is `Atlas-Academy/Playbooks/Read-the-Cert-Not-the-Sign-Log.md`** (from the device-verified Lab-01 `MC-0002`) — every Playbook copies its shape.

- **Symptoms & search terms (required — the findability element, Backlog `#32`).** This is what makes the offline briefcase *findable* when the operator is mid-incident and does not know the "official" name — so it is generous, specific, and plain-spoken. The **filename = the problem in plain, searchable words = the ticket title** (`#32`); this element surfaces the page when he types *what he is seeing, in his own words*. Four required parts:
  - **Verbatim error strings** — the exact text the tool/OS prints, **quoted**, so pasting the error into search lands here (e.g. "*An Active Directory Domain Controller (AD DC) for the domain could not be contacted*"). **One error string per bullet** — don't `·`-join several onto one line; a distinct bullet per error differentiates them, narrows the reader to the right failure mode, and (optionally) tags each with the mode + the step that resolves it. Keep it honest (`POL-0001`): a symptom string the estate has really seen is fine to list; any *command output* stays 🟡 until a real read-back is pasted.
  - **Plain-language symptom phrases** — how a human describes it: "looks connected but I can't reach it", "the port is up but the host is dead", "it worked yesterday", "my change didn't take".
  - **Aliases / also-known-as** — the same problem said different ways; synonyms; the tool / feature / protocol / device names involved, so a search for any of them finds it.
  - **Keywords line** — a dense line of the terms someone would actually type: device names, commands, port numbers, cert names, the `CM-####` anchor.
  - Anchor the page to `#32` (a reference in the frontmatter Status or `Related`) so the briefcase intent is traceable. This element **subsumes and replaces** the older bare "Symptoms / when you'd use this" heading — keep the "when you'd use this" framing inside it.
- **On this page (required — the quick-nav index).** A short **numbered** table of contents at the top (the sections, and for a multi-cause page its causes→fix), so a mid-incident reader jumps straight to the step they need under the 3-click rule. Keep it terse — section names, not prose. *(Demonstrated on the golden template and `MikroTik-EastWest-Inspect-and-Troubleshoot`.)*
- **① Pin it down (the standard opening move).** Before any command, capture the concrete facts of *this* instance — these facts are also exactly a **ticket's fields** (the briefcase principle), and pinning them stops you diagnosing the wrong instance:
  - the **identifiers** that pin the specific case — source/dest/port·proto, hostname/role, service, device, VLAN;
  - **expected vs actual** — what should happen vs the exact error/behaviour;
  - **scope & timing** — one host or many? started when? what still works?
  - **recent change** — what changed just before (deploy, rule edit, reboot, cert rotation)?
  - (where it applies) **is it even supposed to happen?** — check the owner; a *correct* block/behaviour is a change-request, not a fault.
- **Readability (required).** One idea/command per line. Break a compound step into enumerated **sub-steps (`a/b/c`)**; put the **command**, the **Command-Library reference**, and **Healthy** / **Broken** each on their own line. No semicolon-packed multi-clause bullets — the reader is mid-incident. Detailed is fine; dense is not.
- **Command-first, and point to the fix — not a design doc (required — the action-layer discipline).** A Playbook is the *action layer* (§1): **foreground the exact commands** — the real `show`/`get`/`openssl`/`print`/`systemctl` reads as copy-paste blocks with Healthy/Broken — and **point to the doc that owns the fix** (`POL-0008`) rather than re-deriving it. Each layer keeps its home: the *why* is a `Concepts/` module (link **up**), the fix procedure is the `CM`/`MC`/Build-Guide record (**link to it**, don't restate), the commands are the Command-Library (link **down**). If a Playbook reads like a design doc, the conceptual weight belongs in a Concept and the fix belongs behind a link.
- **Explain the mechanism where a misconception bites (required where one exists).** Where a step turns on a **common wrong assumption** — e.g. *"a certificate has a usable default SAN"* — include a short **plain-language "how it actually works, and why the naive assumption fails"** note, grounded in the real mechanism/standard (the RFC, the vendor default, the exact config key). This is what makes the offline briefcase *teach* rather than just list, and it's what turns a one-off fix into a transferable lesson. *(The golden-template reference `Playbooks/Read-the-Cert-Not-the-Sign-Log.md` demonstrates both — its "How a SAN is actually configured in OpenSSL (and why there's no safe default)" section, and the command-first diagnosis path that links to the Lab-CA Build-Guide for the fix.)*
- **📸 Capture markers (SS-001).** At each read-back that *proves* the answer (which rule matched; the fix confirmed), add a **📸** naming what to capture — healthy vs broken — as reference/rebuild evidence. Store beside the playbook (an `images/` subfolder); **never a live secret** (`POL-0002`). Captures are produced by **running the real `show`/read commands in a scenario**, so they land 🟡→✅ as the playbook is exercised on the device — not pre-fabricated.
- **The diagnosis path.** Numbered steps, each *check → command → healthy vs broken → what it proves / where it points next*, reusing the Command-Library entry format and **linking** to it (`POL-0008`), never restating the commands. One idea/command per line; break compound steps into `a/b/c` sub-steps.
- **Per-step provenance (required where the page is anchored to a real incident).** Each diagnosis-path step that a documented incident actually proved carries a **provenance pointer to the `CM-####`/`MC-####` step that proved it** (e.g. *"→ `MC-0002` Step 5"*). It makes the method auditable back to the device record (`POL-0001`) and keeps the incident's home authoritative (`POL-0008` — the CM doc owns the incident; the Playbook links). A step with no real proof yet stays 🟡.
- **Gap / what this closes (optional — the gap-analysis element).** Where the incident behind a Playbook exposed a **structural gap** — a design weakness the current lab closes, or one still open in the partial build — add a short note naming it: *what the gap was, whether the mitigation is device-verified running or still designed-only (⬜/📋), and whether it's a security vulnerability.* This turns a Playbook into a mini gap analysis and links across to the estate's cross-lab **`Atlas-Academy/Lab-01-to-Lab-02-Reconciliation-and-Gap-Map.md`** and the Review-Flag-Register / backlog where the standing risk is tracked. **Optional, not required** — include it only when there's a real gap to name; a routine break-fix with no structural lesson skips it. Keep the evidence rule (`POL-0001`): a gap is "closed" only when the mitigation is verified running, not when it's designed. *(Gap analysis is a key Atlas tool — Backlog `#37`.)*
- **Worked example → the CM/MC doc (where a clean Lab-01 case exists).** When the Playbook is drawn from a real, device-verified incident, add a **Worked example** section that walks that incident through the steps above, **quoting the real read-backs** from the frozen record (`POL-0001`) and **linking to the authoritative `CM-####`/`MC-####`** ("the CM doc owns the incident; this walks it through the steps"). It grounds the abstract procedure in what actually happened and gives the reader the real numbers to expect. Include it whenever a clean case exists; a purely synthetic/seeded Playbook may skip it until one does.
- **Worked log (operator ask).** A short table at the foot — **Date · Who · Time · outcome** — with a row added **each time the playbook is actually run** (`POL-0001`: the outcome is the evidence; an RTO if it's a drill). It tracks *uses*; the **Change Log** tracks *edits to the doc*. Playbooks stay the finished procedure; the distilled how-to / automation **Runbooks** remain the deferred sibling (§2). Existing leaves gain the Worked log **as each is next touched** (`ADR-0049`), not in a bulk pass.

### 6. The Academy anchoring rule (unchanged, restated)
Every entry references a **real Atlas artifact/device** by name (`Academy-Vision-and-Scope.md`). The Academy is the cross-device *teaching + operational-knowledge* layer; it **links to** the device page that owns a fact (`POL-0008`), never restates it.

### 7. Applied one doc at a time, write-when-real
No empty scaffolding (`ADR-0049`): a `Playbooks/` file is written when there is a real problem to capture; the `Playbooks/README.md` index + this standard are the only up-front artifacts. The same structural pattern (a layer index + name-keyed leaves under the 3-click rule) is applied to the other Academy layers **as each is next touched**, not in a bulk pass.

### 8. Playbooks ↔ commissioning checklists (the two-way operational link)
Commissioning **checklists** (the fillable `.xlsx` run-sheets in `00-Atlas-Foundation/Templates/` and each `Devices/<host>/`, Backlog **#33**) and **Playbooks** are the two halves of one operational loop — *build it right* and *fix it when it breaks* — and they **reference each other explicitly**:

- **A checklist links *down* to Playbooks.** Each commissioning checklist carries a **"related Playbooks & Runbooks"** block (on its Cover sheet) mapping *a symptom at a build step* → the Playbook that resolves it (domain join won't complete → `Domain-Join-Fails`; a VM won't boot on Proxmox → `Proxmox-Inspect-and-Troubleshoot`; a path is blocked → `Trace-a-Blocked-Flow`; name resolution fails → `Recover-from-a-DNS-Outage`).
- **A Playbook links *back* to the checklist.** A Playbook whose failure is hit during a build carries a **Checklist** entry in its `Related` section pointing at the specific **phase/step** — the *"check the commissioning checklist for this item"* reciprocal — so the operator re-verifies the causal prereqs (DNS→DCs, time, path to the DCs) before diagnosing.
- **One home per fact (`POL-0008`).** The checklist owns the *build steps + read-backs*; the Playbook owns the *diagnosis + fix*; neither restates the other — they cross-link. A future **Runbook** (automation, `ADR-0048`) joins the same loop when that work lands.

This makes the offline briefcase navigable **both** directions: from a build that stalled → the fix, and from a fix → the build step that should have prevented it.

## Alternatives Considered
- **Build Runbooks now too (a two-type action layer).** Rejected — the operator scoped it: *Playbooks now, Runbooks when we get to automation.* Folding how-to/technique content in now would bloat the layer before the automation work that gives it real examples (`ADR-0048`).
- **No Academy ADR — fold it into the Vision doc + house-style.** Rejected — the operator wanted the *how-docs-are-made* rule recorded as its own decision; a vision doc states intent, an ADR states the standard.
- **Reuse the per-device Standard (`ADR-0037`).** Rejected — that Standard is a *device folder* shape (README/Roadmap/Build-Guide/…); the Academy is organized by concept/command/problem/cert, cross-device.
- **Organize Playbooks by platform (like the Command-Library).** Rejected for the action layer — you search by *the problem you have*, not by platform; a blocked-flow trace spans four platforms. The Command-Library stays platform-first for verification; Playbooks are problem-first and link down into it.

## Consequences
- New `Atlas-Academy/Playbooks/` layer with a cert-mapped index; two real samples this slice (`Trace-a-Blocked-Flow` · `Port-Already-In-Use`).
- `ADR-Index` gains this row (**v1.23 → v1.24**); `Academy-Vision-and-Scope.md` and `Atlas-Academy/README.md` reference this standard and link the Playbooks layer (3-click).
- The cert maps become the *grounding index* for the action layer (a follow-on pass wires the cert-objective cross-links as playbooks are written — ties to `#30`/`#28`/`#16`).
- A **`Runbooks/`** sibling layer is now on the map, **owned by the automation work** (`ADR-0048` / Backlog #19/#7) — built then, not now.
- Backlog `#31(b)/(c)` advances; the ticketing map (`#32`) inherits the name-keyed, ticket-title-shaped Playbook filenames.

## Review Trigger
Revisit when: the automation work starts (stand up the `Runbooks/` sibling then, per `ADR-0048`); any Academy layer needs a second sub-index (the 3-click rule is at risk — re-flatten or re-scope); or a cert map's objectives are wired in and reveal the Playbook template needs a field. Also revisit the platform-vs-problem organization if a cross-platform Playbook proves unwieldy.
